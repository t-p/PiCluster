# Replace Tailscale subnet routing with a Cloudflare Private Network Route

**Status**: accepted

`nextcloud` and `imap-server` each ran a privileged Tailscale sidecar advertising a subnet route to `192.168.88.0/24`, purely by accident duplicated across both pods — not deliberate HA. We're replacing both sidecars with a single Cloudflare Zero Trust Private Network Route advertised by the existing cloudflared tunnel, reached via WARP client in split-tunnel mode, OTP-email enrollment (single user, two personal devices).

The route targets the Kubernetes **Service CIDR** (ClusterIP range), not the physical LAN. Pod IPs were rejected as the target — they churn on every reschedule. The LAN was rejected too, on reflection: it's a wider blast radius than needed (exposes the entire home network — NAS, router, every other device — not just these two apps).

**Split DNS abandoned.** The original plan was a Cloudflare Gateway resolver policy for `*.svc.cluster.local`, pointed at CoreDNS, so devices could use cluster-internal service names. This does not work: `.local` is a reserved mDNS/Bonjour TLD (RFC 6762). Client OSes (confirmed on macOS) intercept any `.local` query for multicast DNS resolution before it ever reaches a configured unicast DNS server — the query never reaches Gateway at all, confirmed via empty Gateway DNS logs for the domain. Kubernetes' default cluster domain (`cluster.local`) collides with this on every client device, not just this one. Renaming the cluster domain (e.g. to `cluster.internal`) would fix it but is a K3s-wide change (kubelet + CoreDNS on every node) not justified for reaching two apps. Devices instead connect directly to the stable ClusterIPs (`nextcloud`: `10.43.27.203`, `imap-server`: `10.43.95.132`) with no DNS step involved. As a consequence, `nextcloud`'s NodePort and `imap-server`'s LoadBalancer (klipper-lb) are reverted to plain `ClusterIP` — the tunnel becomes the only path in, closing the side door that let anything on the LAN reach these apps directly. `nextcloud`'s `NEXTCLOUD_TRUSTED_DOMAINS` was updated to the ClusterIP accordingly.

Trade-offs accepted deliberately: Cloudflare becomes a single point of failure for both public app access and private/remote access (previously independent of Tailscale). `imap-server`'s Dovecot stays without its own TLS listener — plaintext IMAP now relies entirely on the tunnel's transport encryption rather than an app-level TLS layer, same trust model shift as the network access itself.

Migration complete: Tailscale sidecars, RBAC, ServiceAccounts, the `tailscale-state` PVC/ConfigMap, and the `tailscale-auth` secrets are removed from the cluster; both `nextcloud` and `imap-server` Services are `ClusterIP`; the corresponding machines are removed from the Tailscale admin console. Verified working from two devices (laptop, phone) before removal, per the additive-first migration order.

**Dual access path for `nextcloud`, discovered during migration.** Cloudflare Access (gating public hostnames on the existing tunnel) needs an interactive browser login, which breaks non-browser clients (Nextcloud's desktop/mobile sync app talks to the API directly, not via redirect-and-cookie). Two paths now coexist for the one app:
- **Browser**: `https://nextcloud.pfeiffer.pw` — public hostname, real Cloudflare-issued TLS, gated by a Cloudflare Access policy (Allow, email).
- **Sync/app clients**: `http://10.43.27.203` (ClusterIP) directly over the Private Network Route — no Access involved, gated instead by WARP device enrollment.

`imap-server` only uses the ClusterIP path (`10.43.95.132:143`) — IMAP isn't a browser-redirectable protocol, so Access doesn't apply to it; a `tcp://` published route was considered but not built, since the existing path already works.

**Related finding, not caused by this migration**: the account's `Access` product had no plan selected at all, meaning every existing published application route (`argocd.pfeiffer.pw`, `git.pfeiffer.pw`, `ssh.pfeiffer.pw`, `n8n.pfeiffer.pw`, `photos.pfeiffer.pw`, `monitor.pfeiffer.pw`) was fully public with no Cloudflare-level auth in front of it. A Free plan was activated and an Access policy added for `nextcloud.pfeiffer.pw`; the other five routes were not addressed as part of this migration and remain unprotected at the Cloudflare layer (whatever auth those apps have themselves is the only gate).
